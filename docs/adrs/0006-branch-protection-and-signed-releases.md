# ADR-0006: Branch protection and signed releases

## Status

Accepted

## Date

2026-05-19

## Context

The repository's main branch (`main`) is the production OSS surface. Any unreviewed direct push to `main` can introduce regressions, IP boundary violations, or accidental disclosures that are immediately visible to downstream consumers and to the public GitHub events feed.

Three failure modes motivated this ADR:

1. **Burst-push anti-pattern:** pushing many commits in a single batch to `main` reads as a sudden burst rather than steady development, regardless of how the underlying work was actually paced.
2. **Force-push on public `main`:** destroys commit provenance; makes the public events feed inconsistent (old SHAs still fetchable, but history differs); creates confusion for downstream consumers who have cloned.
3. **Unverified releases:** a release tag without an SBOM, without CI green, or without human sign-off is not an auditable artefact.

## Decision

**Branch protection on `main`:**

- Direct push to `main` is blocked. All changes must arrive via pull request.
- At least one CI check (`ci.yml` — typecheck + test + lint + REUSE lint) must pass before merge.
- Force-push to `main` is permanently blocked (GitHub setting, not just a convention).
- Rebase-and-merge is the only permitted merge strategy (squash merge disabled, merge commit disabled) to preserve per-commit history on `main`.

**One-commit-per-push to public branches:**

- Each `git push` to any branch under `ariada-org/ariada` lands at most one new commit. Burst-push is blocked by the pre-push hook which fails if the push would land more than one commit ahead of the tracking remote branch. Exceptions are a maintainer-only history-removal force-push, and the initial multi-commit publication that established the public history.

**Release signing (current baseline):**

- Every release tag is created via `gh release create` after CI passes on the tagged commit.
- Each release includes CycloneDX SBOM (`sbom.cdx.json`) and SPDX SBOM (`sbom.spdx.json`) generated by `sbom.yml`.
- GPG/Sigstore Cosign signing of release artefacts is planned for a subsequent iteration (see §«Alternatives considered»).

**Planned hardening (next iteration):**

- Sigstore Cosign artefact signing on all release binaries and SBOMs.
- OpenSSF SLSA provenance level 2 attestations via `slsa-github-generator`.
- OpenSSF Scorecard target ≥7.5.

## Consequences

- **Positive:** prevents the burst-push pattern from reaching the public events feed; protects commit provenance; outside readers see a steady individual-commit cadence rather than batch dumps.
- **Negative:** one-commit-per-push requires a trickle-push workflow when a feature branch has multiple commits — mitigated by a launchd cron that pops one commit every 10–30 minutes.
- **Neutral:** the rebase-only merge strategy means PR authors must keep branches up to date with `main` before merging — standard discipline for active repositories.

## Alternatives considered

- Squash merge: collapses per-commit rationale into a single message — loses the engineering story that outside readers follow.
- GPG tag signing as the current baseline: requires key management infrastructure not yet in place; Sigstore Cosign is the planned replacement (keyless, via GitHub OIDC).
- No branch protection: insufficient for a public-OSS repository.
